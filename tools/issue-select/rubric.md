## How to read dates and roles

Every day-count threshold below is measured against the **reference
date**: in eval mode, the `captured:` date printed in the bundle's
repo-facts block; in live mode, today. "Maintainer" means a commenter or
opener whose association is OWNER, MEMBER, or COLLABORATOR. Bots
(usernames ending in `[bot]`, or `zulipbot`, `github-actions`, `cursor`,
`dependabot`) are never maintainers for the purposes of a check, even
when their association says MEMBER.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| `repo-alive` | Repo-facts block: the `archived:` flag on the repo line and the `last push to any branch` date. | Pass only if `archived: no` AND the last push is 180 days or fewer before the reference date. An archived repo fails regardless of push date. | required |
| `maintainer-active` | Repo-facts block: the dates and authors of the "last 5 default-branch commits". | Pass if the newest of the five commits is 90 days or fewer before the reference date, and that commit was authored by a human, or is a bot merging a human's pull request ("Merge pull request #N from <user>/..."). Fail if the newest commit is older than 90 days, or all five commits are bot-only housekeeping (dependency bumps, leaderboards, autogenerated docs) with no human PR merged. | required |
| `not-assigned` | Repo-facts block: the `this issue: assignees:` field. | Pass only if it reads `none`. Any named assignee fails. | required |
| `no-open-pr` | Repo-facts block: the `linked PRs:` field with the state of each PR; plus any comment in the thread that links a pull request opened for this issue. | Pass if no linked PR is in state `open` (PRs from forks count too) and no comment dated within 90 days before the reference date announces a PR opened for this issue. PRs in state `closed` or `merged` do not count as claims here. If the field reads `none` and no comment links a PR, pass. | required |
| `no-active-claim` | The comment thread: comments such as "I'll take this", "working on this", "can I work on this", "I'd like to work on this", "I've started looking at this", with their dates and whether a maintainer replied. | Pass if there is no claim comment dated within 90 days before the reference date. A claim comment older than 90 days is stale and passes. A claim within 90 days still passes only if a maintainer replied to it saying the issue is open to anyone else. A maintainer stating the issue is reserved for a named person ("we are not looking for other contributions") fails regardless of dates. | required |
| `bounded-scope` | Issue title, body, labels, the linked-PRs field, and the comment thread. | Fail if ANY of these holds: (a) the issue is a tracking, umbrella, meta, or "megaissue": its body lists 3 or more other issues as sub-items, or it explicitly invites many separate PRs over an area of the codebase rather than one change; (b) the issue is a usage or support question rather than a change to make; (c) the issue is a feature or enhancement request (not a bug, not a documentation task) whose opener is not a maintainer AND no maintainer comment in the thread agrees to a specific approach; (d) 2 or more linked PRs are in state `closed` (abandoned attempts, not merged); (e) a maintainer comment in the thread says the fix touches core internals or that the design is still undecided. Otherwise pass. A terse body, a short list of examples of one behaviour, an acceptance-criteria checklist, a docs task that touches several pages in one PR, or a bug without reproduction steps is NOT a scope failure: grade the size of the work asked for, not the polish of the write-up. | required |
| `ai-policy-ok` | Repo-facts block: the `contribution policy` line (CONTRIBUTING.md, AI policy files, templates). | Fail only if the policy states an outright refusal of AI-generated or AI-assisted contributions (wording such as "we do not accept AI-generated code", "AI contributions are prohibited/banned"). Conditions pass: disclosure, "you must understand and test every change", human review required, "strongly discouraged", "PRs without human review are closed". "no CONTRIBUTING.md", "no stated policy", or "no statement on AI" passes. An `AGENTS.md` file passes. | required |
| `newcomer-label` | Issue labels in the issue header. | Pass if labels include `good first issue`, `help wanted`, `easy`, `Easy to Fix`, `beginner`, or an equivalent newcomer label. | preferred |
| `maintainer-responsive` | Repo-facts block: the "maintainer first-response sample". | Pass if at least one sampled issue received a maintainer comment within 30 days of being opened. | preferred |
| `starting-point` | Issue body and comments. | Pass if the text names at least one concrete file, function, module, or reproduction command a newcomer can start from. | preferred |

## Verdict rule

- `accept` if and only if every `required` check grades `pass`.
- Any `required` check graded `fail` gives `reject`.
- `unclear` on a `required` check counts as `fail`: a first issue whose
  liveness, claim status, scope, or policy cannot be verified from the
  evidence is not one to take. Use `unclear` only when the evidence the
  check names is genuinely absent from the bundle, not merely thin.
- `preferred` checks never change the verdict. Report their grades; on
  an accepted issue they rank it against other accepted candidates
  (more preferred passes ranks higher).
